# 운영 안내서 (초안)

> 2026-11-28 작성. 저장소에서 확인한 내용만 적었다. **"확인 필요"** 표시는 Vercel · Supabase · GitHub 설정 화면에서만 볼 수 있어 아직 확인하지 못한 항목이다. 확인하면 이 문서를 고친다.

## 1. 구성

| 무엇 | 어디 | 비고 |
|---|---|---|
| 웹 | Vercel (`vercel.json`, 리전 `icn1`) | PR마다 미리보기 배포. main 머지 시 운영 자동 배포 여부 **확인 필요** |
| DB · 로그인 | Supabase (Postgres, Google 로그인) | 환경 변수 이름: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` |
| CI | GitHub Actions (`.github/workflows/ci.yml`) | 린트 · 타입 · 단위 테스트 · 빌드, 로컬 Postgres에서 pgTAP |

- Supabase 환경 변수가 없으면 사이트는 카탈로그만 보이는 모드로 빌드된다(예약 · 로그인 꺼짐).
- **확인 필요**: Supabase 환경 변수가 Vercel의 Preview 환경에도 걸려 있는지. 걸려 있으면 PR 미리보기가 실제 예약 데이터를 읽고 쓴다. Production에만 두거나 스테이징 프로젝트를 따로 둔다.

## 2. 배포

1. 기능 브랜치 → PR → CI 통과 → main 머지.
2. 머지 뒤 운영 주소에서 홈, 글래스 상세, 예약 폼을 연다.
3. 문제가 있으면 3번(되돌리기)을 먼저 하고 원인은 그다음에 찾는다.

## 3. 되돌리기

- **웹**: Vercel 대시보드 → Deployments → 직전 정상 배포 → "Promote to Production"(또는 Instant Rollback). 코드는 그 뒤에 `git revert`로 PR을 올려 맞춘다.
- **DB**: 마이그레이션은 자동으로 되돌릴 수 없다. 되돌리는 마이그레이션 파일을 새로 써서 적용한다. 데이터 손실이 있으면 백업에서 복구한다(5번).

## 4. DB 마이그레이션 (대표 승인 필요: 관문 3)

- 스키마 변경은 `supabase/migrations/`의 파일로만 한다.
- CI는 일회용 로컬 DB에만 적용한다. **운영 적용은 수동이다.**
- 운영 적용 순서:
  1. PR이 머지되고 CI의 pgTAP이 통과했는지 확인한다.
  2. 대표 승인을 받는다(노션 컨펌 요청).
  3. `supabase migration list --linked`로 운영에 아직 적용되지 않은 파일을 확인한다.
  4. `supabase db push --linked`로 적용한다. **`--include-seed`는 절대 붙이지 않는다**(`supabase/seed.sql`은 테스트 기기 5대를 넣는다).
  5. 적용 뒤 예약 한 건을 만들어 보고 취소한다.
- `npm run db:reset`은 로컬 전용이다. `--linked`를 붙이면 운영 DB가 지워진다.
- **확인 필요**: 지금 운영 DB에 어느 마이그레이션까지 적용됐는지. `20261101000000_reservations.sql` 머리말에는 "Not applied anywhere yet"이라고 적혀 있다.

## 5. 백업

- **확인 필요**: Supabase 요금제의 자동 백업 주기와 보관 기간, PITR 사용 여부.
- 복구 연습을 한 번도 하지 않았다. 스테이징 프로젝트가 생기면 한 번 해 본다.

## 6. 감시 (지금은 없음)

| 항목 | 상태 |
|---|---|
| 새 예약 알림 | 없음. 관리자 페이지(`/admin`)를 직접 열어야 보인다 |
| 오류 추적 | 없음. Vercel 런타임 로그만 있다(보관 기간 짧음) |
| 접속 감시 | 없음 |
| 방문 통계 | 없음 |

서비스 도입은 비용이 들 수 있어 대표 결정 사항이다(관문 5). 그전까지는 **하루 두 번 `/admin`을 열어 새 요청을 확인한다.**

## 7. 장애가 났을 때

1. 손님 영향부터 줄인다: 웹 문제면 3번대로 되돌린다.
2. Vercel 로그에서 오류 페이지의 digest 값으로 서버 기록을 찾는다. 로그에 손님 이름 · 연락처를 남기거나 옮겨 적지 않는다.
3. 진행 중인 예약에 영향이 있으면 손님에게 먼저 연락한다.
4. 아래 양식으로 `docs/ops/incidents/YYYY-MM-DD-제목.md`에 기록한다.

```
# 제목 (YYYY-MM-DD)
- 언제부터 언제까지:
- 손님에게 일어난 일:
- 원인:
- 조치:
- 다시 안 생기게 할 일:
```

## 8. 보안 메모

- `.env`와 키는 저장소에 넣지 않는다. 운영 DB에는 직접 접속하지 않는다.
- 모든 응답에 보안 헤더를 붙인다(`next.config.ts`). 스크립트 CSP는 아직 없다. HSTS는 Vercel이 붙인다.
- Node 버전은 `.nvmrc`(CI가 읽음). **확인 필요**: Vercel의 Node 버전이 같은지.
